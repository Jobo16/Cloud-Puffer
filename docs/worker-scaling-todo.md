# 渠道与 Agent 执行扩容 TODO

状态：待实施（2026-11-18）。本清单是改造顺序，不表示功能已完成或容量已验证。

## 目标与边界

- 同一账号的回合继续按顺序执行；不同账号可由多个执行器并行处理。
- 渠道连接只有一个有效持有者；Agent 执行器可独立增加实例。接收、执行、投递分别保留可恢复的状态，不因进程重启重复执行业务工具或盲目重发渠道消息。
- 先使用现有 TypeScript、PostgreSQL、pg-boss 和 Docker Compose。Go、NATS、Kubernetes 与通用插件平台不属于这轮改造；只有实测瓶颈或明确的新接入需求出现时再评估。
- 当前实现见[架构](architecture.md)：`src/worker.ts` 同时持有全库锁、渠道连接和 4 个 Agent 执行槽；`scripts/migrate.ts` 建立 `key_strict_fifo` 队列，`singletonKey` 为账号 ID。

## P1：先扩容单实例，并控制积压

- [ ] 将 Agent 并发数从 `src/worker.ts` 的固定值改为服务端配置；在相同测试负载下比较 4、8、16 个执行槽。同步核对 PostgreSQL 连接池、模型供应商并发/限流及成本，选择能稳定运行的值，不直接以 16 作为生产默认值。
- [ ] 为全局积压设置可观察的上限和过载处理：新请求能看到排队或明确的稍后重试结果；已有请求不因新流量无限后移。保留当前账号级限额和按用户顺序。
- [ ] 监测并处理 `key_strict_fifo` 中永久失败的队首任务；失败账号不能在无人察觉时一直被挡住。恢复动作必须先核对该轮业务写入和渠道投递状态。

## P2：拆分渠道持有者与 Agent 执行器

- [ ] 从 `src/worker.ts` 拆出**渠道进程**：独占现有全库锁，负责微信轮询、QQ/Telegram 连接、连接状态恢复及本地设备超时清理；保持一个实例，不给每个用户创建进程或容器。
- [ ] 拆出**Agent 执行进程**：只领取并处理云端 Agent 任务，不持有渠道独占锁；允许两个及以上实例消费同一个 pg-boss 队列。验证跨实例的账号级 FIFO、不同账号并行与取消行为。
- [ ] 将渠道回复交给渠道进程处理。执行器完成运行后在数据库中保留可恢复的待投递状态；若使用独立投递队列，完成状态与入队同事务提交。投递前重查账号绑定、取消状态和回复凭证。明确失败可按渠道规则处理，超时或结果未知不自动重发。渠道投递不得长期占用 Agent 执行槽。
- [ ] 保留 Web、渠道和本地设备现有的账号归属、去重与幂等规则；进程拆分不能让同一轮被云端模型和本地设备同时执行。
