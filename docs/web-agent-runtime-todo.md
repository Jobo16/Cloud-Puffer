# Web Agent runtime 待办

当前优先完成网页对话的可靠运行与排队体验。微信、QQ、Telegram 的新增能力和实机验收暂缓；现有渠道代码继续维护必要的安全与故障修复。每一阶段先用测试库、模型替身和 staging 验证，再考虑扩大并发。

## 已有基础

- Web 请求与队列任务同事务提交；请求标识去重，同一账号按顺序执行，不同账号可并行。
- 模型工具写入按运行与工具调用去重；取消后阻止继续写入。进程中断后不盲目重放已经执行的工具。
- 网页通过事件流看到排队、执行、输出与失败状态；运行最长 120 秒。
- [x] 网页显示每轮已排队时间；Worker 记录不含消息正文的排队与执行耗时日志。

## P0：把失败和等待变得可见

- [ ] 在 staging 建立 Web 运行基线：按日志汇总排队等待、执行耗时、失败原因和积压，至少记录 P50/P95 与最长等待；区分模型限流、模型超时、服务重启和用户取消。
- [ ] 用测试模型覆盖运行中取消、模型断流、工具执行后失败、Worker 重启和队首任务永久失败；确认网页状态与实际持久化结果一致，失败不会静默卡住或重复执行业务写入。
- [ ] 量测网页事件流对数据库的查询量和连接数；随着用户增长，避免每个连接每秒读取完整工作区状态。先用数据确定是否需要按运行增量推送。

## P1：用实测数据改善容量

- [ ] 用模型替身重复测试至少 20 个账号、10 个并发 Web 请求，包含短回复、接近 120 秒的慢回复和突发流量；记录等待、吞吐、CPU、内存、数据库连接及模型请求数。
- [ ] 根据测量结果确定可接受的排队时间与过载行为；请求无法及时开始时给出明确状态，不让积压无限增长。
- [ ] 比较当前 4 个执行槽与更高并发，核对模型限流、数据库连接和成本后选择配置值。当前共享 Worker 的渠道独占锁限制多实例扩容；确需多实例时，先把渠道连接持有者与 Web Agent 执行器分开，再验证跨实例账号顺序和取消。
