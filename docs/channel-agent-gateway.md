# 渠道与 Agent 接入方向

状态：网页、微信、QQ 和 Telegram 共用账号级入站运行与来源投递；Telegram 仅完成代码和测试替身验证，尚无真实 Bot 验收。本地 Codex 已经由网页 API、HTTP 设备桥和连接程序完成真实文字回复；浏览器点击、OpenClaw、手机渠道和生产验收尚未完成。Octop 渠道进程尚未接入。

各模块优先复用的上游项目、许可证和本机可验证结果见[开源复用记录](research/open-source-reuse-2026-11-12.md)。

## 目标

云端继续为多个账号提供网页、对话、事项、记忆和额度。目标是让网页、微信、QQ、Telegram、WhatsApp、飞书等收发渠道都能接入同一条账号级主对话，并持续增加其他可接入渠道；平台能力、登录与收发限制按渠道分别实现和验证。每个账号可选择云端现有 Agent，或由该用户电脑上的连接程序调用本地 Codex/OpenClaw。用户电脑只主动连接云端，不开放入站端口。当前实现范围见本文状态与[开发文档](development.md)。

## Octop Gateway 的适用范围

参考仓库为 [TencentCloud/octop-gateway](https://github.com/TencentCloud/octop-gateway)，本地调研基线 `224ed078ce20042fb5fa59240d6e3c7c34bcd67f`（`octop-gateway` 1.0.3，MIT）。其 `InboundMessage`、`MessageEvent`、`BaseChannel` 和 `ChannelManager` 分别处理消息归一化、回复事件、平台收发、渠道调度。`tenant_id` 和 `channel_id` 用于隔离渠道实例；它们不代替本项目经过验证的用户身份、业务数据归属和额度规则。参考源码保存在忽略提交的 `.research/octop-gateway`，不把整套 Python 源码复制进 TypeScript 应用。

Octop Gateway 是 Python 3.12+ 的渠道库，没有 JOJOBOT 的网页账号、PostgreSQL 业务记录、Agent 选择或本地 Codex/OpenClaw 连接。其会话锁和队列在进程内，默认媒体后端为本机文件系统；本项目仍需使用数据库保证运行顺序，并将用户文件放在私有对象存储。若采用其平台适配器，应作为独立渠道进程运行，以受认证的内部接口交换消息；现有 Web、Worker 和业务库仍为账号、会话、运行与投递状态的权威来源。平台能力、登录方式和媒体行为须逐项验证，不能因 Octop 支持某平台就标记为本项目已接入。

Telegram 首版直接复用 MIT 许可的 [grammY](https://grammy.dev/)：它可在现有 TypeScript Worker 中长轮询 Bot API，避免为一个渠道新增 Python 进程与内部传输。Octop 的消息归一化和渠道边界仍是设计参考；未来渠道若只有稳定的 Octop 适配器，再评估独立渠道进程。Telegram 绑定只允许已验证网页账号，Bot 只接收已绑定发送者的私聊文字；媒体、群聊及主动通知尚未开放。

## 接入边界

```text
网页 / 微信 / QQ / Telegram / WhatsApp / 其他渠道
             ↓ 渠道消息：渠道实例、外部身份、消息 ID、内容、回复目标
账号绑定与主对话：验证归属、去重、额度、入队、持久化
             ↓ 账号 ID、运行 ID、用户输入
Agent 路由：云端现有 runtime / 用户电脑上的连接程序
             ↓ 运行事件：输出、工具结果、完成或失败
主对话与投递记录 → 发起消息的网页或渠道
```

- 渠道适配器只处理平台协议、收发限制与回复凭证。外部发送者必须先映射到已验证的 JOJOBOT 账号；未知或已解绑身份不能启动 Agent。
- JOJOBOT 为每个账号保留一条主对话和现有账号级 FIFO。`source + 外部消息 ID` 参与去重；重绑后的旧回复目标不可用于新连接。
- 云端 Agent 的工具仍走服务端业务模块。网页是同一消息入口，但事项、记忆、账号设置等操作继续使用已认证的业务 API。
- 渠道提交成功只表示平台接受；未知结果不自动重发。媒体与主动发送必须分别检查平台能力，不能压平成“文本回复成功”。

## 用户电脑上的 Agent

本地连接程序通过出站 HTTPS 轮询连接云端，使用与用户账号绑定、可撤销的设备令牌。云端只向该设备分配所属账号的运行，并保存运行状态；Codex/OpenClaw 的登录凭据和本地工具留在用户电脑。设备离线时显示不可用，不静默改用云端模型或重复执行已有运行。

当前开发预览通过本机 CLI 执行一轮：Codex 使用 `codex exec` 的只读沙箱，OpenClaw 使用 `openclaw agent --json`，两者均先在本机终端要求用户确认，不自动向 OpenClaw 渠道投递。每轮传入云端主对话的近期历史，使用独立本地会话。这样只承诺完整文字回复，不承诺逐 token 流式输出、云端事项/记忆工具、Codex 交互式授权或跨轮本地工具状态。进一步接入 [Codex app-server](https://developers.openai.com/blog/codex-as-a-platform)及 [OpenClaw Gateway WebSocket](https://docs.openclaw.ai/gateway/external-apps)协议后，才能保留其完整运行事件和授权流程。

JOJOBOT 主对话是跨渠道记录的权威来源。本地 CLI 每轮使用新的会话 ID，接收最多十二轮的有限历史；中断后不自动重新执行，以免重复调用本机工具。

### 最小连接协议

- 用户登录网页后生成一次性显示的设备令牌。数据库只保存 SHA-256 摘要，用户可在网页撤销设备；所有设备请求验证令牌并按设备所属账号取运行。当前尚无单独的短期配对码交换步骤。
- 本地程序每两秒通过 HTTPS 轮询本账号指定设备的运行，运行期间每十秒报告状态。运行只允许首次领取，重复提交相同结果幂等；撤销设备或取消运行后的结果被拒绝。
- 本地运行中断或设备离线超过两分钟时标记失败，不自动重放可能执行过工具的请求。当前只在完成后提交完整文本，尚不持久保存中途输出。
- 默认每轮由用户电脑确认执行；涉及本机文件、命令或外部服务的授权继续交给 Codex/OpenClaw 本地客户端。配对码、设备令牌和本地 Agent 凭据都不得写进对话或日志。
- 网页展示当前 Agent 及设备在线状态；仅当所选本地设备在线时接受新运行。切换 Agent 只影响新运行，不把已经领取的运行改派给另一个 Agent。

### 数据归属与使用量

每个账号独立保存 Agent 选择、设备及其撤销状态、运行。设备只收到所属账号的当前输入与必要历史；对话原文、事项和记忆仍由云端业务模块管理。本地 Agent 不使用云端模型积分；其本机模型用量目前不在网页展示。每个渠道的原始发送者身份先通过现有绑定表解析为账号，再选择该账号的 Agent。

### 验收门槛

至少验证两个账号与两台设备互不串用；撤销设备后领取和提交均失败；同一外部消息只创建一次运行；离线、进程崩溃、重复完成及取消不重复调用本地工具；网页和微信/QQ/Telegram 能接续同一主对话；渠道仅报告实际提交结果。Codex 与 OpenClaw 分别在真实用户电脑上完成文字回复、授权请求和中断恢复检查。新渠道还须额外验证平台登录、媒体、回复窗口与重绑行为。

## 迁移顺序

1. 现有 TypeScript 服务让网页、微信、QQ、Telegram 共用账号级入队规则，完成结果按来源投递；保持各平台的协议和绑定逻辑独立。
2. 增加账号绑定的本地设备连接和运行状态，再分别对接 Codex app-server 与 OpenClaw Gateway。先支持文字、取消和失败状态；授权请求必须能在用户电脑上处理。
3. Telegram 已用 grammY 接入当前 Worker；继续用真实 Bot 验证身份映射、重复更新、断线、未知投递和多账号隔离。其他渠道优先找现成适配器，只有需要跨语言组件时才引入独立进程。

本地 Agent 增量使用 `0007_greedy_hairball.sql`；Telegram 绑定与连接使用 `0008_tearful_paibok.sql`。原有微信/QQ 验收结论仍只适用于原实现。Octop 的平台适配器、媒体后端和调度器均未引入生产代码。
